Security

Report a vulnerability through GitHub's private vulnerability reporting on this repository, or by email to security@ballerine.com. Do not open a public issue.

What Pointe is

A voice call into your Claude Code sessions. Words you speak can make a session do work, so a stranger who reaches the daemon, or a web page that reaches it, must get nothing. The rules below are enforced in code and have tests, mostly in tests/test_security.py and tests/test_orchestrator.py.

Who may connect

  • The daemon's HTTP port listens on the loopback interface only. Call audio uses the same port, as a WebSocket, so it never leaves loopback either. Only pointe pair opens another address (see Phone access).

  • Every route except /voice/health needs a secret. Scripts send a per-daemon token (~/.claude-voice/token, 0600). The page opens once with a key in its address (bin/voice-open), which becomes an HttpOnly, SameSite=Strict cookie.

  • That cookie lives on a private name, <hash>.localhost. Cookies ignore ports, so one set on plain localhost would reach any server you open on another port.

  • Origin must match Host exactly, for HTTP and for WebSocket. This stops other web pages and DNS rebinding.

  • Only the same origin can frame the page, which blocks clickjacking.
  • An empty secret opens nothing.

What a spoken word can do

With the default brain, a permission prompt is approved only when all of these hold:

  • The daemon read the request out itself, from what will run and not from the description the session's model wrote. readout.py says a shell command only when every part of it is on an allowlist: known programs (git, rm, cp, grep, curl, npm test, pytest, ...), each with a table of known flags, in plain pipelines. It says every program, every file written, every URL's host, every git remote, and the flags that change what can be lost. Anything else (unknown programs or flags, $, backticks, globs, braces, subshells, heredocs, several lines, wrappers such as sudo or env, VAR= other than a few harmless ones, more than 25 words, or a credential-like value such as a key, a token or password=: readout.redact) is not read out. Two adversarial reviews found 24 ways around earlier versions; each is now a test. File tools are read as their path. The line ends in "Should it?", with no consent word, so it cannot come back through the speakers as a yes.

  • A request that is not read out is approved by a tap, never by voice: the page, and the phone app, show the exact request with Approve and Deny. A tap counts only for the request still pending. The terminal can answer it too.

  • It was the last thing the bot said. No model wording can open this window, and any other speech closes it. So can being cut off. The request is then read out again.

  • You said a yes and nothing else, begun after the read-out ended. "Okay, tell me more", "yes, and run the linter", "okay so", and "no worries" do not count.

  • The yes came within 120 seconds of the read-out, on the active session.

The short form drops output-only flags and shortens paths plainly inside the project to their name. In our own Claude Code history, about 13% of shell commands can be read out; the rest need a tap or the terminal.

Text-to-speech is not a proof. It can mispronounce a command, and you may not catch a dangerous flag by ear, so the page shows the exact request. If you want no voice approvals, set approvals: terminal.

Starting a session

Pointe can start a new coding-agent session (docs/features/new-session.md). It is the one thing a spoken word can do that creates a process, so it is fenced on every side, in code with tests (tests/test_new_session.py):

  • Where. Only in a folder from a list the daemon builds: folders of the sessions on the voice, of sessions that joined in the last 30 days, and folders added in Settings. A request's folder is looked up in that list; a path is never trusted, from speech, the page or the phone. sessions.folders is refused from the phone's key and from a page opened over the network, so the list grows only at the Mac.

  • How. Never with permission prompts skipped: Claude Code gets --permission-mode default, Codex and OpenCode no override, and a Codex thread that would run with no approvals and no sandbox is archived and refused (harnesses.base.refuse_bypass, harnesses.codex.bypasses).

  • Who. By voice, always a read-back of the agent, folder, machine and name, taken from the user's own words, then a plain yes within 60 seconds: not the read-back heard back, not typed words, and with the voice lock on only the owner's voice. That yes never approves a waiting request. On the iPhone and the Mac app, Start asks for Face ID or Touch ID. Meeting mode and Challenge me cannot start anything.

  • Left open. Code running as you can register a session from any folder (it could before), which makes that folder "recent". A paired phone can start a session with a first prompt in an allowed folder; it could already send requests to the sessions there.

Adding sessions

Pointe can join sessions the user already runs, and reopen one they ran this week, from a description (docs/features/add-sessions.md). Joining gives the voice that session's transcript, sends and (where the harness allows) its approvals, so it is fenced the same way as a start, in code with tests (tests/test_attach_*.py):

  • Who. By voice, nothing joins on the first sentence: Pointe reads back what it found, from the user's own words, and joins on a plain yes within 60 seconds, or on a pick from the list it read back ("the second one", "both"), bound to exactly those sessions. Not the read-back heard back, not typed words, and with the voice lock on only the owner's voice; that yes never approves a waiting request. On a screen, a tap sends back a key from the Mac's own listing (never a path), and on the iPhone and the Mac app Join and Reopen ask for Face ID or Touch ID. Meeting mode and Challenge me cannot add sessions.

  • Whose. Only this OS user's: the config dirs Pointe knows that the user owns, processes the daemon may signal, and inbox sockets that are sockets owned by the user and not links. Claude Code's inbox socket is read from its own record of the process (sessions/<pid>.json), checked against the session claude agents --json names.

  • Reopen. A Claude Code session reopens with claude --resume <id> --permission-mode default in a new terminal window, never with a skip flag; a Codex thread that comes back with no approvals and no sandbox is refused.

  • Approvals. A Claude Code session whose Pointe plugin was not on when it started keeps its prompts in its terminal; Pointe says so in the read-back and never claims otherwise.

  • Left open. Code running as you could already register any of your sessions; a paired phone can now add any of your sessions listed on the Mac, after Face ID. Discovery reads up to 64 KB from each end of a week of transcripts.

Night shift

A night shift (docs/features/night-shift.md) is the one time Pointe sends to sessions while nobody is listening, so its rules are code with tests (nightshift.py, tests/test_night_shift.py):

  • It starts on your yes. The sessions and tasks are cut from your own words, read back with the caps, and started on a plain yes within 60 seconds, under the rules of a new session's yes. On a screen, Start shift is its own button; the apps ask for Face ID or Touch ID.

  • Pointe never answers an approval. A permission request from a session on the shift is held, neither allowed nor denied, for up to 12 hours, and recorded word for word in the ledger. It is answered only by you: the read-out and your yes, a tap, or the session's own terminal. No function of the shift can reach the code that delivers a verdict (tested by reading the source).

  • Every message is a fixed template around your own task. No model writes a send at night. Each one repeats that nothing destructive or outward-facing beyond the task may be done.

  • Nothing is widened. No permission mode or allow rule changes; a new session on the plan passes New session's checks.

  • Caps and stop. 8 hours and 40 messages by default, at most 12 and 200. "Stop the night shift" counts from any voice, as a no does; it only ends sending.

  • Left open. A session told to "choose the most defensible answer" makes judgment calls you did not see: they are on the ledger with what changes otherwise, and the briefing leads with them. A paired phone can start a shift, as it can already send requests. hooks/hooks.json lets the permission hook wait 12 hours (it was 5 minutes): the daemon still lets an ordinary request go after 280 seconds, and a daemon that stops drops the connection.

Drive mode (optional)

Drive & walk mode (drive.py) only narrows the rules above; it never widens them. You enter it yourself ("drive mode", "מצב נהיגה", or the Drive button); it is shown on the page and the phone, and it ends with the call (at once on a hang-up or the idle timer; after 5 minutes when the link drops and does not come back). While it is on, a spoken yes approves a request only when, on top of every rule above:

  • the read-out allowlist can say it whole (a credential-like value is never read out: such a request waits for a tap);

  • it loses nothing (drive.road_safe, its own allowlist): read-only programs, tests, mkdir, touch, git status, diff, log, show, fetch, pull, add, commit, push (no force, delete, mirror, +ref or :ref, no --amend, --no-verify, --rebase or --prune, no add -f, which adds what .gitignore keeps out), plain curl GETs, and edits inside the project. rm, mv, cp, redirects into files, git reset, clean, rebase, checkout, stash, npm run, make, gh and edits outside the project wait for a tap, as does any edit in a session on another machine (its folder is not on this disk);

  • with a voiceprint stored, the yes itself is a strong match for your voice (speaker.strong), at any lock level.

A no counts from any voice. A tap answers any request, as always: the page and the app hide the buttons while driving and "I've stopped" leaves the mode, after which the request is read out again normally.

Owner-voice lock (optional)

Settings → Voice lock learns your voice on a call and checks each thing said against it, on this Mac. Levels: Off (as above), Approvals (a spoken yes counts only in your voice; a no counts from anyone), Commands (other voices never reach the voice model; they are listed as ignored, with their words, in memory only), Everything (the same, and their words are not shown or kept).

  • It only narrows. A match is never consent: every rule above still has to hold for your yes. It adds "and it was your voice"; it removes nothing else.

  • It fails closed. When it cannot tell (no model yet, a model error or a score slower than 0.6 s, under 0.3 s of audio, a damaged voiceprint), the speech counts as not yours for what the level guards. A tap, Face ID, the terminal and typed text still work, so this costs convenience, never control. Deleting the voiceprint turns the lock off.

  • It is not authentication. It is a check against the bystander (a spouse, a colleague, a TV), not an attacker: a recording of your voice can pass it, and a short "yes" is weakly scored (it counts on its own only after a strong match within a minute, on the same device's voiceprint). Measured on synthetic voices only: see bench/results/speaker.md.

  • Model: 3D-Speaker ERes2Net (Apache-2.0), run locally by sherpa-onnx, downloaded once from the sherpa-onnx GitHub release with a pinned SHA-256. No vendor sees the audio for this check or the voiceprint.

Whisper mode

Whisper mode (whisper.py; "whisper mode", "מצב לחישה", or the Whisper button) changes how the call sounds, never what a word can do. The bot plays at half volume, the microphone is raised (x2.5, soft limiter) with a whisper profile for the voice detector, and replies are kept short. A whispered yes or no goes through exactly the same check as a spoken one (tested by running the approval cases with the mode off and on and comparing the outcomes). It is never an approval path and never lowers the voice lock: a voiceprint is learned from your normal voice, and a whisper scores low against it (no synthetic whispered sentence reached the strong-match threshold in bench/results/whisper.md), so with the lock on a whispered yes usually does not count and the request waits for a tap. Drive mode holds it: while driving the bot plays at full volume and whisper mode applies again when drive mode ends. With a challenge on, both apply; whisper mode adds nothing a challenge takes away.

Audio briefings

A briefing ("brief me on the night", or scheduled) reads; it never sends or approves. Each part reaches the voice model bracketed as data, with "send nothing, approve nothing"; a send still needs your fresh speech, and the briefing's own words close the window for a spoken yes, so a yes after "lantern waits for your approval" brings the read-out again instead of approving. A permission is named in a briefing ("a permission approval"), never quoted. Credentials are masked with the same rule as the read-out and the alerts (readout.mask) before a session's record reaches the reading model, and again on what it writes. No briefing is spoken during a meeting or brain dump; a meeting that starts stops it.

A realtime front (CLAUDE_VOICE_FRONT=gemini or openai) speaks by itself, so there is no line to bind a yes to: it can deny by voice, but only the terminal approves.

What sessions report is data for the voice model, not instructions to it:

  • A model gate checks each new send against what you just said. The gate is a model and can be wrong. It lowers the risk of prompt injection, it does not remove it.

  • A correction ("no, the other session") or a yes to "which session?" skips the gate, and sends the earlier text word for word, whatever the model wrote.

  • A request reaches another session only if you said its name, or said yes to a question that named it.

  • ask_about_session has no gate. It only reads, and the answer goes to the speaker.

Keys

  • Keys come from the environment or the macOS Keychain, and reach the daemon only.
  • Claude Code sessions never receive them from Pointe, and git runs without them.
  • They are not in command lines: scripts pass the token to curl through --config.
  • The page shows vendor errors with key values replaced. Logs hold an error's text as the vendor wrote it.

What leaves your machine

What Where
Your speech, and your dictionary, session and folder names and the names in session notes as hints The ears vendor
Session content, including transcripts The brain and reader vendors
What the bot says, which can quote session content The mouth vendor
What you said, each session's latest lines, goal, folder path and up to 40 file names The gate vendor
When you add sessions by voice and a few fit about as well: each one's title, folder name, age and up to 8 keywords (at most 8 sessions, never a transcript) The gate vendor

With the microphone set to push to talk (Settings, on the page or the phone), no audio leaves your machine unless you hold the talk control (or toggled it on), plus 0.4 s after you let go. The daemon enforces this: it drops the audio before the voice detector and every vendor, whatever a client sends. A press ends by itself after 90 s. One exception: during a meeting you started (it asks for consent and shows a recording indicator), the room's audio goes to the meeting's speech vendor without a press; talking to Pointe outside the meeting stream still needs one.

In fully local mode (pointe local), none of these goes anywhere: no key is read, from the environment or the Keychain, so no vendor can be reached, and the text-model server listens on loopback only. See docs/features/local.md.

With "Voice stays on your Mac" (pointe local voice), no audio goes to a vendor: ears and mouth run on the Mac, the Soniox and ElevenLabs keys are never read, meeting mode is off, and every path that would stream audio out (cloud ears or mouth, a realtime front, the echo guard's mirror stream, meeting ears) is refused in code. The brain, reader and gate vendors still receive text. See docs/features/voice-stays-local.md.

With openai_url set, the OpenAI text models are served by a host you choose (Azure OpenAI, for example): that host receives what the brain, reader and gate vendors would, over https only, and the OpenAI key is sent there and never to OpenAI, so OpenAI's audio services are refused. See docs/features/openai-url.md.

Choose vendors you are allowed to send that content to. pointe doctor shows which ones are in use. Pointe has no server and no telemetry, and the page loads nothing from outside your machine.

No telemetry from its libraries either. onnxruntime, which runs the voice detector, the voice lock and kokoro-onnx, connects to Microsoft's telemetry collector (*.events.data.microsoft.com) when it loads, from native code (seen with 1.31.1). Pointe sets ORT_DISABLE_TELEMETRY=1 before onnxruntime can load, in every setup: no_telemetry.py is imported first by every module that can reach it, and bin/voice-daemon, bin/pointe, bin/voice-doctor and bin/claude-voice export it for their child processes. tests/test_no_telemetry.py fails if any module reaches onnxruntime without it. Measured: with it set, no connection to Microsoft in isolation or during an audio suite (docs/features/voice-stays-local.md).

Supply chain

Pointe is installed from this repository and runs with your keys, so what reaches your machine matters as much as what leaves it. The inventory, with each source's pin and its verification, is docs/security/supply-chain.md.

  • How it is built. There is no build and no package: claude plugin install clones main, and everything runs from that checkout with uv run --locked. Python packages come from PyPI at the exact versions and SHA-256s in uv.lock; uv refuses a mismatch. The Node channel (launch mode only) installs with npm ci --ignore-scripts from its lockfile. uv itself, when setup installs it, comes from the installer for one version, checked against a SHA-256 before it runs (bin/install-uv). Models are fetched by SHA-256 (release files) or by commit (Hugging Face), pinned in assets.py, and refused on a mismatch. Nothing in bin/, hooks/ or plugin/ fetches code at run time; the page loads nothing from outside your machine; onnxruntime's telemetry is off.

  • How to verify. In Claude Code's plugin folder: git rev-parse HEAD against the tag on GitHub, uv lock --check, and uv run --locked pytest -q tests/test_supply_chain.py, which checks the pins, the allowlists and the egress list against the tree. CI runs the same on every push, plus pip-audit over every locked version, and Dependabot opens grouped weekly bumps that a person reviews (.github/).

  • How to report. A suspicious dependency, download or install step is a vulnerability: use GitHub's private vulnerability reporting on this repository or security@ballerine.com, as at the top of this page.

  • Known limits. You get main at install time (release tags are not signed yet); bin/voice-connector pulls twingate/connector:1, a moving tag, by design; a model you name by hand (pointe local --model) is not pinned.

Files

~/.claude-voice is 0700. It holds the token, the page key, session notes, daemon.log, and journal.jsonl, a full record of each call with what you said and session content. With phone access it also holds the pairing secret, a TLS key and the connector's tokens. With the voice lock it holds voiceprint/ (0700; one file per enrolled device, 0600): biometric data, computed and kept only on this Mac, deleted from Settings → Voice lock on the page or in the app. models/ holds the speaker model. With fully local mode, local/ holds the text-model server's environment, its log (which may hold session content in errors) and config.before-local.json, the choice pointe local off restores; the models themselves sit in the Hugging Face cache (~/.cache/huggingface) and Kokoro's in ~/.cache/pipecat. The journal records an ignored utterance's length and score, never its words. briefings.json (0600) keeps the last seven briefings, written out per session and redacted. night-shifts.json (0600) keeps the last seven night shifts: tasks, what sessions reported and any approval request they waited on, with credentials masked. dictionary.json (0600) holds the names you added or fixed (Settings → Dictionary on the page or in the app shows, edits and deletes each one); it never takes a yes, no or stop word, anything readout.mask would hide, or words from a meeting. Delete what you no longer need.

Machines

Sessions on another Mac or a Linux host join the voice through a node there (docs/multi-machine.md). The Mac with the call (the hub) keeps every rule above for them.

  • Pairing. The hub makes a one-time code: single use, 10 minutes, about 40 bits, kept only as a hash in memory, and accepted only while it is outstanding. Each address may try 5 codes at once, then about one a minute, checked before the code is compared, so one address cannot try enough to cancel the invite. After 20 wrong codes from all addresses together it is cancelled, and the page, the app and pointe hub invite say how many came and from which addresses. A guesser behind the same connector as your machine can delay it by a minute, not lock it out. Making it from the app needs Face ID. The node checks the hub certificate's SHA-256 against the fingerprint in the invite before it sends anything. The hub then shows the node's name, address and key fingerprint, so you can see that the machine that paired is yours.

  • The link. The node dials the hub's TLS listener (the phone's) and proves its 256-bit key with an HMAC over a fresh challenge from the hub; the key itself never crosses. One connection per key: a copy of a node cannot connect while the node is connected. pointe hub revoke <name>, Settings → Machines on the page (two clicks) or in the app (a confirm, then Face ID) ends it.

  • What crosses. To the hub: each session's transcript and permission requests, with credentials masked on the node (readout.mask), names, folder paths and up to 40 file names; and, only when you look for sessions to add, each listed session's name, folder, agent, age, title, keywords and first and last request (160 characters each), never its transcript path, socket or account. To the node: your requests to its sessions and your answers to its prompts. A node holds no vendor key. Its sessions' content reaches the hub's vendors, as the hub's own sessions' does; pointe node join and pointe node status name them.

  • Approvals, checked twice. The node re-checks voice and notification approvals against its own copy of the request: a spoken yes counts only if the hub read out exactly the text the node computed from the unmasked request, and a notification's Approve only for a request the node can read out. A tap is trusted from the hub, as the hub's own page is trusted. What a tap approves on the hub's screens is the masked preview; the exact unmasked request is in the session's own terminal. A node can refuse remote taps on requests it cannot read out: "remote_taps": "readable_only" in its ~/.claude-voice/config.json (off by default).

  • Offline. When a node's link drops, every prompt it held goes back to its own terminal, and a late answer is refused as stale. The screens show no Approve or Deny for a session that is offline.

  • Files. On the hub, nodes.json (0600) holds each node's key; anyone who reads it can act as any node toward this hub. On a node, node_keys/<hub id> (0600). Mirrors of remote transcripts sit under harness/remote/ (0700, files 0600), and are deleted 7 days after their session left.

Known limits

  • Code running as you is trusted. It can read the token and forge anything: register a session, read the journal, inject a prompt, or approve a permission prompt through a session's channel. Claude Code's child processes receive the token in launch mode. Pointe does not defend against code already running as you; a separate OS user would.

  • Launch mode uses --dangerously-load-development-channels. Claude Code requires this flag for a channel outside its allowlist. It loads only channel/voice-channel.mjs from this repository, and Claude Code shows a warning at start.

  • A spoken yes in conversation is not an approval. See the safety model in the README. Permission prompts are different: they are answered through Claude Code's PermissionRequest hook, and its deny rules still apply.

  • Voice is not authentication. Anyone your microphone can hear can answer a prompt, unless the voice lock is on; even then, a recording of your voice can pass it.

  • The page key does not rotate by itself. It lasts until you delete ~/.claude-voice/page_key. It also passes through a browser's command line when bin/voice-open runs, which other users on a shared Linux machine can read.

  • While the voice holds a prompt, the terminal also shows it, and either can answer. It waits up to 280 seconds. If you answer in the terminal, the daemon may not notice at once, because of how it reads a closed connection (Low; a known limit).

  • Two pages with the key can both be in a call. Keep it to one.

The Mac app

The Mac app (macos/, docs/mac-app.md) is another client of the daemon on the same Mac. It changes no rule above and adds no listener.

  • It is the page, to the daemon. It connects to 127.0.0.1 only and sends the page's key as the page's cookie, read from ~/.claude-voice/page_key (0600) into memory at each connect: never stored, logged or put in a URL.

  • It checks who listens first. Before the key is sent, the listener on the port must be the process the daemon's pid file names, or its child, as bin/voice-daemon checks; another program on the port gets nothing. A request that cannot connect drops the verified address, and the check runs again before the key is sent anywhere.

  • Approve asks who is there. A click on Approve in the window asks for Touch ID, an Apple Watch or the account password (the page on the Mac asks for nothing); Deny never asks. The daemon still takes the click only for the request that is pending. A notification's Approve follows the same daemon rule as the phone's.

  • No model key. The app checks only whether a key is in the Keychain (attributes, never the secret). Adding one runs the plugin's own pointe key window.

  • The shortcut is a Carbon hot key: macOS tells the app about that one combination. It has no Accessibility and no Input Monitoring permission and sees no other key. While a press is open it reads that one key's up or down state.

  • One entitlement, the microphone, under the hardened runtime. Not sandboxed: it starts the plugin's voice-daemon ensure and reads the state folder. It makes no outbound connection and looks for no updates.

  • Known limit, as above: code running as you can read the page key the app reads.

Phone access (experimental, off by default)

bin/voice-remote adds an HTTPS listener for a phone on a private network. Remote requests need the configured name and a pairing cookie. The listener is decided by the port that accepted the connection, never by Host or forwarded headers. Limits: the pairing link is a lasting secret with no rotate command, despite the word "link", so treat it as a password. bin/voice-remote off leaves the connector and its tokens in place. And bin/voice-connector pulls twingate/connector:1, a moving tag. Call audio over this path is one TCP connection.

The iPhone app

  • Pairing. pointe pair tailscale|wifi|host <name> makes a TLS certificate for that one name, and a QR code with its SHA-256 and the phone's own key (phone_key, 0600). The app keeps both in the Keychain and talks only to that Mac.

  • Pairing from the page (Settings → Phone, phone_pairing.py). The page lists the routes this Mac has (Tailscale, a name you set up, the Wi-Fi) and shows a QR code made on the Mac, with no outside service. The QR holds the listener's name, its certificate's SHA-256 and a one-time code, not the phone key: single use, 5 minutes, about 40 bits, kept only as a hash in memory, with the same bounds on wrong codes as a machine invite (5 at once per address, then a slow refill, checked before the code; the invite cancelled after 20 from all addresses together). The app checks the certificate first and only then sends the code to /voice/phone/pair, which answers the phone key. That route takes no other secret and refuses a request with an Origin (a web page). The routes that make a code, list routes and unpair answer only the page on this Mac, by its cookie: the phone key, the daemon token and a page opened over the TLS listener get 403. The status shows paired phones by name and time only; neither the status nor the log carries a code, a link or a key. Choosing another route makes a new certificate (the page says so first): every phone and machine paired before must pair again.

  • A key for each phone. Each pairing from the page mints that phone its own 256-bit key, returned once; phones.json (0600) keeps only its SHA-256, with the phone's name and when it paired and was last seen. Every route that takes the phone key takes any paired phone's key; each check compares against every stored key in constant time, with no early exit. Unpair (two clicks) signs out that phone alone, from its next request, and ends its call if it has one up; another phone stays connected. Unpair all signs out every phone. Pairing the same phone again retires its old key.

  • The shared key from before. phone_key (0600), which pointe pair put in its QR code before per-phone keys, still works, as one phone named "Paired phone" until the app reports its name (an X-Pointe-Device header). So the upgrade signs no one out. pointe pair show still prints that old link with that key, and mints it again if it was unpaired: the terminal path is unchanged, and Unpair on the page revokes it like any other phone.

  • Pinning, and App Transport Security off. The app accepts exactly the certificate it paired with, and nothing else, CA-signed or not. iOS's App Transport Security can't be scoped to a name you pick (a Twingate or VPN name), and it refuses a self-signed certificate before the app's own check runs, so it is off for this app. The pin is the stronger check: ATS trusts any CA-issued certificate for the name, and the pin trusts one certificate.

  • What the phone key opens: the call socket, status (sessions, the last turns of the conversation, the words being heard), approve, the brain dump (/voice/dump, /voice/listen), switching the active session, hanging up, and the voice lock (/voice/voiceprint: enrol, delete, level; the app asks for Face ID before lowering the level or deleting), briefings (/voice/briefings: the last seven, start, skip, stop, and the schedule), Show while it says (/voice/artifact), the dictionary (/voice/dictionary: list, add, edit, delete), drive mode (/voice/drive: on, off), and the conflict alarm (/voice/conflicts: dismiss, or ask one side as typed words, which never approve). Not the model's whole context, renaming, modes, or anything a Claude Code session uses.

  • Show while it says reads source files. The page on this Mac always shows the files and test output the voice talks about. The phone key, and a page opened over the TLS listener, get nothing (no showing in status, 403 from /voice/artifact) until show.on_phone is on (Settings → Show while it says; the app asks for Face ID to turn it on). Once on, a leaked phone key can read what the voice showed: the last ten reports' files, inside each session's folder only. Either way the daemon never takes a path from the caller, shows only tools that ran (never a tool still waiting for approval), refuses files outside the session's folder after resolving symlinks, hidden files and secret-looking names (.env*, *.pem, *secret*, *key*, id_*, *credential*, ...), binary files and files over 512 kB, and masks secret-looking values (known token shapes, private keys, name = "..." and unquoted name: value for secret-like names, URL passwords, and the values of this machine's own key variables) in file lines, diffs, test output and commands. Diffs read HEAD with git cat-file, never git diff, so a repository's filters and diff drivers do not run.

  • Approve needs Face ID or the passcode; deny never does. One opt-in exception: with "Approve from notifications" on (alerts.watch_approve, off by default; the app asks for Face ID to turn it on), a notification's Approve needs an unlocked iPhone or a watch on the wrist instead. The daemon accepts it (via: "notification") only for a request it can read out, bound to that request's id (alerts.py).

  • Notifications (phone, watch, desktop) show only the read-out form of a request, never its full text or the model's description; a request that cannot be read out shows only its tool. Credential-like values follow the same rule as the voice (readout.redact): never shown, never said.

  • Revoke: Unpair in Settings → Phone. The phone paired from the terminal can also be revoked by deleting ~/.claude-voice/phone_key; it takes effect at the next request. Pairing again with the same name keeps the certificate, so a browser that trusts it keeps working.

  • Tested on a real iPhone over Twingate, and in the simulator against a real host name.
