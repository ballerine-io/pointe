# Security review, 2026-11-23: Claude Mythos 5.2

**Reviewed:** Pointe 1.21.0, a pre-release build (2026-11-23). **Fixed in:** Pointe 1.23.1, a pre-release build
(2026-11-23). **Re-reviewed twice** by the same five passes: after the first fixes, and after the second (both
pre-release builds of 2026-11-23).

The versions named here are pre-release builds, before the public history started at 0.8.0; every fix below is in 0.8.0.

## Result

The first review reported 33 findings and one suspected crash, in five areas: 1 high, 13 medium, 16 low and 3 info.
Three were the same issue reported by two passes. Each was checked against the code. All were confirmed, except three
that describe the documented design (NP-4, SS-9, AA-4), which SECURITY.md now states more plainly. Every confirmed high
and medium is fixed, each with a test that failed before the fix, and so are most lows.

The re-review found every fix in place. Because each pass reads the code afresh, it also reported 31 findings the first
pass had not, two of them rated high: a read-out that said a quoted argument as "some text" (R-AV-1), and the IPv6
loopback address the daemon did not hold (R-NP-1, rated medium by one pass and high by another). Both were in 1.21.0
before this review. Both are fixed in the same release, with every new medium and most lows; those not fixed are listed
with the reason. A second re-review, after those fixes, rated nothing high or critical; its confirmed mediums that
touch approvals, pairing or the logs are fixed too, and the rest are listed as open.

**Open after 1.23.1:** no critical or high finding; 2 medium (R3-AA-1 and R3-NP-4 with R3-SS-2, both needing
another account on the Mac and a race); the lows and the residual risks of fixed findings listed in each table.

No finding showed a way in for someone with no secret and no access to the Mac: the loopback guard, the one-time
pairing codes, certificate pinning and the machine link's handshake held in every pass.

## Scope and method

- **Model:** Claude Mythos 5.2 (`claude-mythos-5-2`), through Claude Code (`claude -p`), on a separate Claude Code account.
- **Tools:** read only: `Read`, `Grep`, `Glob`, and `git log`, `git show`, `rg`, `ls` through the shell. The model
  could not edit, run code or tests, or reach the network through a tool. Findings rest on reading the code; ours rest
  on running it.
- **Passes:** five, one per area, each with the same instructions and its own focus. The runner is
  [`tools/security_review.sh`](../../../tools/security_review.sh); the re-review was run with it.
- **Triage:** a maintainer checked every finding against the code, wrote a test that reproduces each confirmed one
  and fails, fixed it, and ran the full offline suite (about 4,300 tests) and the Swift package tests.

### The prompt

Each pass received this text, with `<FOCUS>` replaced by its area's focus:

> You are performing a security review of Pointe, an open-source voice layer for coding agents (Python daemon serving a
> local web page and a TLS listener for paired phones, Claude Code/Codex/OpenCode adapters, permission-approval relay,
> iOS and macOS apps in Swift). Read SECURITY.md, docs/security/, docs/harnesses.md and docs/multi-machine.md first for
> the intended threat model. FOCUS: `<FOCUS>`
> Read the actual code. Report only real, specific issues with file:line evidence, an exploit scenario, severity
> (critical/high/medium/low/info) using CVSS-style reasoning, and a concrete fix. Also list what you checked and found
> sound, and any assumptions. Do not modify files. Output markdown with sections: Summary, Findings (one subsection
> each: title, severity, location, scenario, fix), Checked and sound, Not covered.

| Pass | Focus |
|---|---|
| `network-pairing` | Network exposure and authentication: the local HTTP server on 127.0.0.1 (origin/CSRF/DNS-rebinding/CORS checks, token handling), the TLS phone listener and certificate pinning, pairing (QR secret, invites, rotate/off), multi-machine hub/node links, remote session tokens, anything reachable from the LAN or a VPN. |
| `approvals-voice` | Approval and voice safety: what a spoken word or a tap can approve or send, the permission-hook relay and hold logic, read-back binding, voice lock/owner binding, meeting mode and night shift rails, prompt injection from session transcripts or meeting audio into the brain that could cause an unwanted send/approval, attach-by-voice joining sessions. |
| `secrets-supply` | Secrets and supply chain: Keychain usage and naming, how keys reach processes (env, argv, logs), logging/redaction, crash/debug output, the install path (uv, link-pointe, ~/.local/bin), plugin hooks, GitHub Actions pinning, dependency lock, the egress allowlist vs real outbound hosts, openai_url. |
| `web-page` | The web page the daemon serves (ui.html and its JS): XSS through session names/transcripts/meeting notes, unsafe HTML insertion, message/event handling, clickjacking, service-worker or storage of secrets, the phone browser path. |
| `apple-apps` | The iOS and macOS apps (apps/PointeKit, apps/ios/, apps/macos/): certificate pinning and pairing storage, Keychain/UserDefaults usage, URL schemes and deep links, Face ID/Touch ID gates, local network permissions, the Mac app's daemon start, AppleScript/automation, entitlements. |

## Findings of the first review

Severity is the model's. Status: **fixed** (in 1.23.1, with a test), **by design** (the documented behaviour, with the
reason), or **accepted** (a known limit, with the reason).

### Network and pairing

| ID | Finding | Severity | Status |
|---|---|---|---|
| NP-1 | The phone listener checked a page's `Origin` by host name only, so a page served on another port of the same name, which the browser treats as same-site and sends the pairing cookie to, could open the call socket and post to the daemon. Also reported as WP-1. | Medium | Fixed: the `Origin` must be exactly `https://<host>:<port>`, for HTTP and WebSocket. |
| NP-2 | A `pointe://pair` link replaced the iPhone's pairing without asking. Also reported as AA-1. | Medium | See AA-1. |
| NP-3 | `pointe node join` wrote the hub's answer to a path built from a hub-chosen id, so a malicious invite could write a file anywhere the user can (`../../.ssh/authorized_keys`). | Medium | Fixed: every field of the hub's answer must have the form the hub makes (16 or 64 hex characters, a valid name) before anything is written. |
| NP-4 | A phone key can turn on Show while it says, Approve from notifications, and make a machine invite, which SECURITY.md presented as gated by Face ID. | Low | By design, now documented: Face ID is the app's check, and a leaked phone key can already approve any pending request. SECURITY.md now says exactly what a leaked key can do, and to Unpair and rotate. |
| NP-5 | `pointe pair rotate` and `pair off` changed the certificate but left every phone key, machine key and the browser pairing secret valid, and a running daemon kept honouring them. | Low | Fixed: both sign out every phone, browser and machine, and a running daemon follows within seconds. |
| NP-6 | Before a machine proves its key, the listener held its socket with no cap and read messages of any size. | Low | Fixed: a frame-size limit and a cap on sockets waiting to prove a key, per address and in total. |
| NP-7 | SECURITY.md's list of what the phone key opens was incomplete. | Info | Fixed: the list now matches the code, and a test keeps them equal. |

### Approvals and voice

| ID | Finding | Severity | Status |
|---|---|---|---|
| AV-1 | A yes sent a meeting's action items when only three had been read back ("and 1 more"), with owners and dates never said. | Medium | Fixed: every item sent is read back with its owner and date; above five, they are sent from the end sheet only. |
| AV-2 | With the voice lock off, anyone heard in a meeting could take the owner's seat by saying "Pointe, that's me", including after a stream reconnect. | Medium | Fixed: with no voiceprint, the seat comes only from the words that started the meeting or a tap. Accepted residual: the speech vendor can label a guest's turn as the owner's. |
| AV-3 | The yes to a read-back (start, close, add sessions, night shift, action items) followed looser rules than the yes to a permission: "yes, but skip the deploy" counted, as did a yes to a later question or one said over the read-back. | Medium | Fixed: one check for every read-back, with the permission prompt's rules (a plain yes, after the read-back ended, while it is the last thing said). Read-backs no longer end with a consent word. |
| AV-4 | A change of the active session left the other session's yes window open, so a yes to one session's question could approve another's request. | Low | Fixed: a change of active session closes every window; the request is read out again. |
| AV-5 | Typed words could confirm a start, a join, a close or a night shift. | Low | Fixed: a typed or corrected utterance never confirms a read-back. |
| AV-6 | The conflict card's Ask sent model-written text as the user's own words. | Low | Fixed: the question goes to that session directly, marked as a conflict check, never as the user's words. |

### Secrets and supply chain

| ID | Finding | Severity | Status |
|---|---|---|---|
| SS-1 | Vendor keys were inherited by programs the daemon starts, including the `claude -p` copy of a session. | Medium | Fixed: every child gets an environment without key variables, keys read from the Keychain stay in the daemon's memory, and a test fails on any spawn that does not use the helper. |
| SS-2 | `/pointe:voice` and `/pointe:setup` pre-approved any `pointe` subcommand, `open` and `echo`, so a steered session could run a bypass-mode session or open a script without a prompt. | Medium | Fixed: only the exact commands each file runs are pre-approved, and `pointe start` refuses every permission-bypass flag. |
| SS-3 | Scripts ran inline Python from the session's folder, so a `json.py` in a repository would be imported in its place. | Medium | Fixed: isolated mode (`python3 -I`) everywhere, enforced by a test; the Keychain and dialog tools are run by absolute path. |
| SS-4 | Environment variables such as `ANTHROPIC_BASE_URL` would send keys and session content to another host. | Medium | Fixed: removed from the daemon's environment at start (given back only to the Claude Code it starts), and every vendor client names its host. |
| SS-5 | The voice model's context was passed on a command line, visible to other local users. | Low | Fixed: passed on stdin. |
| SS-6 | Scripts sent the token without checking which program listened on the daemon's port. | Low | Fixed: one shared check before every request that carries the token or the page key. |
| SS-7 | The logging library's default output could print variable values, including keys, in tracebacks. | Low | Fixed: replaced, with value printing off; key values are also masked in every log line. |
| SS-8 | Generic Keychain names from before 1.20.0 were still read. | Low | Fixed in part: with `openai_url` set, only Pointe's own item is read. Accepted otherwise, so a key saved before 1.20.0 keeps working; documented. |
| SS-9 | Keychain items are readable by any program of the user through macOS's `security` tool. | Info | By design (code running as you is trusted), now documented. |
| SS-10 | Gaps in the supply-chain gate. | Info | Fixed: the egress scan covers every source file, and the key check no longer follows a redirect with the key. Accepted: CI's two audit tools run with their own dependencies unpinned (the job holds a read-only token and no secret; pinning needs a new dependency group). |

### The page

| ID | Finding | Severity | Status |
|---|---|---|---|
| WP-1 | Same as NP-1. | Medium | Fixed with NP-1. |
| WP-2 | No `script-src` policy, and three places that inserted HTML. | Low | Fixed: a policy that allows only the page's own scripts and handlers (by hash), and the three places build nodes. |
| WP-3 | The phone browser's address keeps a key derived from the pairing secret. | Low | Accepted: removing it breaks Home Screen use on iOS. It works only for someone who can reach the private listener, and `pointe pair rotate` replaces it. |
| WP-4 | JSON routes accepted any `Content-Type`, which let a cross-site form post reach them. | Low | Fixed: every POST must be JSON (415 otherwise), on both listeners. |

### The apps

| ID | Finding | Severity | Status |
|---|---|---|---|
| AA-1 | A `pointe://pair` link opened from any app or web page replaced the iPhone's pairing with no confirmation, so the next call could stream the microphone to another server. | High | Fixed: a link opened from outside pairs nothing; it opens the app's scanner. A code scanned or pasted in the app is confirmed with the Mac's address and certificate fingerprint, replacing a pairing needs Face ID, and the old pairing stays until the new Mac answers. |
| AA-2 | Custom URL schemes are not owned, so a code scanned with the Camera could reach another app that claims `pointe://`. | Medium | Fixed in part: the app no longer pairs from links, and every screen says to scan inside the app. Accepted residual: a person who still scans with the Camera, on a phone with such an app installed, can hand it the code. The page then shows a phone they do not recognise, which Unpair removes. |
| AA-3 | The Mac app checked the daemon's port once, then sent the page key to whatever held the port later. | Medium | Fixed: the Mac app no longer sends the key; each request carries a single-use proof bound to the request and to this daemon start. Accepted residual: the browser page still sends its cookie. |
| AA-4 | Face ID gates are enforced in the app, not by the daemon. | Low | By design, now documented: Face ID protects an unlocked phone in another person's hand, not a copied phone key. |
| AA-5 | Scripts the Mac app starts ran under its microphone permission. | Low | Fixed: they are started as their own responsible process, and the app starts none when macOS cannot do that. |
| AA-6 | Pairing codes went to the general pasteboard, including Universal Clipboard. | Low | Fixed: concealed and cleared on the Mac; local only, expiring with the code, on the iPhone. |
| AA-7 | A pairing host containing `:` crashed the iPhone app at every launch (noted by the pass as a suspected crash). | Low | Fixed: such a host is refused, in a new code and in a stored pairing. |

## The re-review

The same five passes ran on the fixed code (`6841698`). Each listed the fixes above among what it checked and found
sound: the exact `Origin`, JSON-only posts, the node join checks, the revocation on rotate, the Mac app's proof, the
pairing flow, the clean child environment, isolated Python and the vendor hosts. The pages' script policy and the
read-back rules were found sound as well.

The re-review also reported findings the first pass had not. Those confirmed are fixed in 1.23.1:

| ID | Finding | Severity | Status |
|---|---|---|---|
| R-AV-1 | A quoted argument was read out as "some text", so a spoken yes could approve a command whose flag or path was never said (`git push '--force' origin main` was read as "git push some text origin main"). | High | Fixed: a quoted flag makes a request unreadable (a tap is needed); a quoted word or path is said; only a search pattern or a message may be said as "some text". |
| R-AV-2 | A flag whose value is not said could swallow a shell operator (`git commit -m ; rm notes.txt` was read as "git commit rm notes.txt"). | Medium | Fixed: such a request is not read out. |
| R-AV-3 | Drive mode's "loses nothing" check refused known flags rather than allowing known ones, and `uniq a b` (which overwrites `b`) passed. | Medium | Fixed: every flag must be one the read-out knows for that program; git's command-running options and curl's upload options are refused. |
| R-AV-4 | In a meeting, the room's words could steer a session look-up, and the answer was spoken unmasked. | Low | Fixed: the look-up must be named in the owner's own question, and answers are masked. |
| R-AV-5 | Paths were shortened without resolving symbolic links. | Low | Fixed: a path that leaves the project is said in full. |
| R-AV-6 | A request preview cut short by the agent could be approved by a tap. | Low | Fixed: it is shown as cut short and can only be denied here; approve it in its terminal. |
| R-WP-1 | The approval card led with the agent's own description, which could push what runs out of view. | Medium | Fixed: the card leads with what runs; the description is a separate one-line note, labelled as the agent's. |
| R-WP-2 | Bidirectional and invisible characters reached the approval card as they are. | Low | Fixed: shown as `\uXXXX`. |
| R-WP-3 | The page's policy restricted scripts only. | Info | Fixed: connections, images, media and forms are limited to the page's own origin. |
| R-NP-1 | The daemon held `127.0.0.1` but not `[::1]`, so another account could listen on the IPv6 loopback address and receive the page key from a browser that tries it first. Rated high by the secrets pass. | Medium / High | Fixed: the daemon and the node hold both addresses and do not start when another program holds either. On Linux (a node), they now also listen on `[::1]` as soon as they bind it, after 1.23.1. |
| R-NP-2 | The two pairing routes read a request body of any size before checking for an invite. | Low | Fixed: no read without an invite, and at most 4 kB with one. |
| R-NP-4 | The web framework's API docs were served behind the page's cookie and loaded scripts from a CDN. | Low | Fixed: not served. |
| R-NP-5 | After `pointe pair rotate`, the old browser cookie worked for a few seconds. | Low | Fixed: refused at its next request. |
| R-NP-7 | The pairing routes told a caller whether a code was live. | Info | Fixed: one answer for every refusal. |
| R-NP-8 | The phone key could not reach the add-sessions route the iPhone app uses. | Info | Fixed (a functional bug, failing closed). |
| R-SS-2 | Fully local mode trusted whatever answered on its model server's port. | Medium | Fixed: only the server it started, or its child. |
| R-SS-4 | Logs and the journal were not masked for key values. | Low | Fixed: every key value the daemon holds, the page key and the token are replaced in each log line. |
| R-SS-5 | `/pointe:voice` still pre-approved setup's commands. | Low | Fixed: it pre-approves only joining; a first run points to `/pointe:setup`. |
| R-SS-6 | CI checkouts kept the job's token in `.git/config`. | Info | Fixed: `persist-credentials: false` on every checkout, checked by a test. |
| R-SS-7 | An existing `uv` on the PATH is used whatever its version. | Info | Fixed in part: a note when it is not the pinned version; documented. |
| R-AA-1 | Adding a second voiceprint needed no Face ID, and the daemon accepted it from the phone key. | Medium | Fixed: the apps ask for Face ID, and the daemon refuses it off the Mac unless the owner's voice matched strongly within the last minute. |
| R-AA-2 | Test settings that pair or unpair the iPhone app were compiled into release builds. | Low | Fixed: debug builds only. |
| R-AA-3 | The Mac app's separate-process start for scripts failed open. | Low | Fixed: it fails closed. |
| R-AA-4 | Deleting the iPhone app does not unpair it. | Info | By design, now documented: Unpair on the Mac. |
| R-AA-5 | The Talk shortcut opens the microphone on a locked phone during a call. | Info | By design (the Action button use), now documented. |

## The second re-review

The five passes ran again after the fixes above. None reported a critical or high finding, and none found a
fix above undone. Each pass again read parts of the code the earlier ones had not, and reported 33 findings, the
highest rated medium. The ones confirmed on approvals, pairing and the logs are fixed in 1.23.1:

| ID | Finding | Severity | Status |
|---|---|---|---|
| R3-AV-1 | The read-out resolved paths against the session's start folder, not the folder the command runs in. | Medium | Fixed: the folder the harness reports is used, and a command run elsewhere is read with that folder first. |
| R3-AV-2 | `cd X ; cmd`, `cd X \|\| cmd` and `cd X \| cmd` were read as if the `cd` had happened. | Medium | Fixed: a `cd` counts only before `&&`; otherwise the request is not read out. |
| R3-AV-3 | A URL path over 30 characters, including a git remote's, was dropped from the read-out. | Medium | Fixed: a URL's path and a git remote are said whole or the request is not read out. |
| R3-AV-4 | A Codex file-change request showed no files. | Medium | Fixed: never read out as a file change; the card shows the folder it asks to write in. |
| R3-AV-5 | An OpenCode request with several resources showed only the first. | Low | Fixed: all are shown, and it is not read out. |
| R3-AV-6 | `python3 -c` code calling a project function was read without its arguments, which could carry a shell command. | Low | Fixed: code whose calls take a string is not read out. |
| R3-AV-9 | `uniq in out` was not said as a write. | Info | Fixed. |
| R3-WP-1 | A double-click on Approve could approve the next request as its card appeared. | Medium | Fixed: Approve on a new card waits 700 ms; Deny does not. |
| R3-NP-1 | A stranger's machine hello with a very long name was written whole to the log, repeatedly. | Medium | Fixed: hello fields are capped before any proof, and refusals are logged once per address per minute. |
| R3-NP-2 | The loopback listeners trusted `X-Forwarded-For`, so per-address limits could be spoofed. | Low | Fixed: no listener reads forwarded headers. |
| R3-NP-7 | WebSockets on the phone listener were not checked for the host name. | Info | Fixed. |
| R3-SS-1 | `pointe pair show` and `link` printed the pairing secret into a session's transcript when an agent ran them. | Medium | Fixed: run by an agent, they open the code as a picture on the Mac and print no secret. |
| R3-SS-3 | Fully local mode checked its model server's owner only at start. | Low | Fixed: checked every 5 seconds, with nothing sent in between. Residual: a port taken within one 5-second window. |
| R3-AA-2 | The Mac app built from source carried the debugging entitlement, so another process of the user could attach to it. | Medium | Fixed: built without it. |
| R3-AA-3 | Unpair on the iPhone needed no Face ID, so a pairing could be replaced without it in two steps. | Low | Fixed: Unpair asks, and needs Face ID. |
| R3-AA-4 | The Pair confirm could adopt a code the camera read after the dialog opened. | Low | Fixed: it pairs only the code it names. |
| R3-AA-5 | The certificate prefix the iPhone shows had nothing to compare against. | Low | Fixed: the page and the Mac app show the same prefix beside the code. |

## Reproduce

```
tools/security_review.sh --ref v1.21.0     # the first review
tools/security_review.sh --ref v1.23.1     # the fixed release
```

The script and the prompt above are the method. A model's review varies between runs; ours is published as found and
triaged, not as a guarantee.
